Sub-chapter 09 · 같은 증상, 세 가지 원인

    같은 손실 곡선이라도
    원인은 셋 — 데이터·모델·코드

    "모델이 안 된다"는 같은 증상에도 진짜 원인은 데이터 문제일 수도, 모델 자체일 수도, 코드 버그일 수도 있다. 그리고 처방은 정반대다. 어떤 증상이 어떤 원인을 가리키는지 매핑하는 진단표.

    08 sub에서 디버깅 결정 트리를 봤다. 그 트리가 끝에서 가리키는 것은 결국 세 종류의 원인 중 하나다 — 데이터 문제, 모델 문제, 코드 버그. 책이 명시적으로 분류하지 않은 이 셋의 구분이 실전에서는 가장 큰 시간 낭비를 막는다. 원인이 코드 버그인데 모델을 키우거나, 원인이 데이터 라벨 오류인데 정칙화를 만지면 며칠을 허비한다.

    이 세 종류의 원인은 책 곳곳에 흩어져 언급되는데, 한 표에 모아 보면 진단이 훨씬 명확해진다. 같은 증상이라도 어느 원인인지에 따라 다음 행동이 완전히 갈리기 때문이다.

    세 가지 원인의 본질

    데이터 문제: 라벨이 잘못됐거나(annotation error), 분포가 편향돼 있거나(distribution shift), 훈련-검증-테스트 분할이 잘못됐거나(data leakage), 입력에 noise·outlier가 많거나. 모델은 멀쩡한데 학습 데이터 자체가 진짜 분포를 못 대표한다. 처방: 데이터 정제, 분할 재설계, 추가 수집, 균형 잡힌 sampling.

    모델 문제: 모델 용량이 데이터 패턴에 비해 부족하거나(과소적합), 너무 크거나(과대적합), 활성 함수가 도메인에 안 맞거나(LSTM이 필요한데 MLP를 썼거나), 정칙화 강도가 잘못됐거나. 데이터는 좋은데 모델이 그것을 못 짠다. 처방: 구조 변경, 용량 조절, 정칙화 조정, 옵티마이저·학습률 재탐색.

    코드 버그: 손실 함수가 잘못 정의됐거나, 그래디언트 계산이 끊겼거나, 데이터 로더에서 축이 뒤집혔거나, 정규화가 누락됐거나, 학습/추론 모드 토글이 잘못됐거나. 데이터도 좋고 모델도 좋은데 구현이 잘못됐다. 처방: 코드 한 줄씩 확인, tiny dataset 테스트, unit test 추가.

    증상 → 원인 매핑표

    다음 표는 실전에서 자주 보는 증상 5가지에 대해 각 원인이 어떻게 갈리는지를 정리한 것이다. 행이 증상, 열이 원인. 한 셀이 "이 증상이 이 원인 때문이면 어떻게 보이는가"다.

    손실이
    안 내려감
    라벨이 일관성 없음. 같은 입력에 모순된 라벨이 다수. 모델이 학습할 신호 자체가 없다. → 라벨링 가이드 재정의.
    학습률이 너무 크거나 작음. 또는 모델 용량이 너무 작아 패턴을 표현할 수 없음. → 학습률 로그스케일 5-7점 재탐색, 용량 ×2.
    옵티마이저 zero_grad/step 누락, gradient 어디서 끊김(detach), 손실 함수 정의 오류. → tiny dataset 5-10개로 0 근처까지 내려가는지 확인.

    격차 큼

    훈련 데이터가 너무 적거나 분포가 좁음. 검증과 훈련의 분포가 다름. → 데이터 추가, 데이터 증강, 분포 매칭.
    모델이 너무 큼 또는 정칙화가 너무 약함. → Dropout↑, weight decay↑, 모델 크기 ↓, Early stopping 켜기.

    학습 도중
    NaN 발생
    입력 데이터에 NaN/Inf 값이 있음. 0으로 나누는 특징 변수. → 데이터 sanity check, NaN 제거 또는 imputation.
    학습률이 너무 커서 발산. 또는 손실 함수가 polynomially explode. → 학습률 ×0.1, gradient clipping (1.0 또는 5.0) 추가.
    log(0) 또는 sqrt(negative). softmax에서 over/underflow. → log·div에 epsilon 더하기, logsumexp trick 사용.
    학습은 잘되는데
    실제 배포에서 망함
    훈련 분포 ≠ 배포 분포(distribution shift). 사용자 행동·환경이 다름. → 도메인 적응(domain adaptation), 배포 환경 데이터로 재학습.
    모델이 일반화 안 됨(overfitting을 검증 세트에서 못 잡음). 검증 세트가 너무 좁음. → 더 다양한 검증 세트.
    학습·추론 코드의 전처리 다름(정규화 통계, 채널 순서). → 학습 코드와 추론 코드의 입력 파이프라인 통일.

    오답이
    특정 패턴
    그 패턴의 데이터가 훈련에 거의 없음. Street View 사례 — 한 자리 잘린 사진. → 그 패턴 데이터 신규 수집·augmentation.
    모델이 도메인의 핵심 변동(rotation, scale)에 견고하지 않음. → 데이터 증강 강화, 또는 모델 구조 변경(invariant features).
    전처리에서 그 패턴이 망가짐(과도한 크롭, 잘못된 정규화). → 전처리 코드 한 줄씩 확인, 실제 입력에 모델 시각화.

    행은 증상, 열은 원인. 같은 증상이어도 어느 열에 진짜 원인이 있느냐가 처방을 완전히 바꾼다. 처방을 정하기 전에 어느 열인지부터 진단하라는 게 11장 디버깅 절의 메타 메시지다.

    왜 원인 진단이 처방보다 중요한가

    실전에서 가장 흔한 시간 낭비 패턴은 이렇다 — 손실이 안 내려간다 → "학습률을 만져 보자" → 안 됨 → "정칙화를 풀어 보자" → 안 됨 → "옵티마이저를 바꿔 보자" → 안 됨 → 결국 라벨에 모순이 있었다는 걸 발견. 며칠 낭비.

    이 패턴이 생기는 이유는 처방을 먼저 떠올리고 원인 진단을 건너뛰기 때문이다. 11장이 디버깅 5종 도구를 "처방"이 아니라 "진단 도구"로 분류한 것은 의도적이다. 도구는 가설을 검증하는 데 쓰지, 무작정 모델을 바꾸는 데 쓰는 게 아니다.

    실용 권고 — 손실이 안 내려갈 때 가장 먼저 할 일은 tiny dataset 5개로 과적합이 되는지 확인이다. 그 한 테스트가 "코드 버그 vs 데이터·모델 문제"를 가른다. 5분이면 끝나고, 그 결과로 다음 며칠의 행동 방향이 완전히 갈린다.

    세 원인이 동시에 있는 경우

    실전에서는 세 원인이 동시에 있을 수 있다 — 라벨에도 노이즈가 있고, 모델 용량도 약간 부족하고, 코드에 미세한 버그도 있다. 이런 경우엔 어떻게 해야 하나.

    책의 메시지는 단순하다 — "가장 큰 원인 하나부터 잡는다." 동시에 셋을 다 만지면 무엇이 해결됐는지 모른다. 가장 의심스러운 하나에 가설을 세우고, 그것만 검증할 한 가지 변화를 준다. 변화 후 결과로 그 가설이 맞았는지 틀렸는지 확인한다.

    가장 큰 원인을 어떻게 고르나. 다음 우선순위가 일반적이다.

    1. 코드 버그를 가장 먼저 의심. tiny dataset 테스트가 5분이라 비용이 가장 낮다. 코드 버그가 있으면 데이터·모델 진단이 의미 없다.
    2. 데이터 문제를 다음으로 의심. 라벨 검수, 분포 확인, 분할 점검. 1-2시간이면 한다. 데이터가 망가져 있으면 모델 튜닝이 의미 없다.
    3. 마지막으로 모델·하이퍼파라미터. 가장 비싸고 시간이 많이 든다. 위 둘이 깨끗할 때만 가치 있다.

    이 우선순위는 "비용 대비 진단 정보가 큰 순서"다. 책이 명시하지 않지만 실무에서 합의된 패턴이다. 디버깅의 핵심은 결국 "의심을 가장 싸게 좁힌다"는 한 줄에 담긴다.

    한 줄 요약

    같은 손실 곡선이라도 데이터 문제일 수도, 모델 문제일 수도, 코드 버그일 수도 있다. 처방은 정반대이므로 원인 진단 없이 처방 적용 금지. 진단 순서는 tiny dataset(코드) → 라벨/분할(데이터) → 하이퍼파라미터/구조(모델). 다음 sub에서는 이 모든 사이클을 얼마나 빠르게 도는가가 왜 결정적인지를 본다.
